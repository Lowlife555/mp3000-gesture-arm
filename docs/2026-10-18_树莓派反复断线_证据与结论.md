# 2026-10-18 树莓派反复断线 —— 证据与结论

> 本文只记录**实测到的事实**与**由此得出的结论**；推测一律标注"推测"。
> 所有时间均为 Europe/London（BST）。

## 一、现象

树莓派（`mp3000pi-niyoujia` / `192.168.1.66`）在 2026-10-18 下午反复从网络中消失。
用户的感受是"又断联了"，看起来像死机、必须断电才恢复。

## 三、已排除的原因（均有实测依据）

| 排除项 | 依据 |
|---|---|
| 过热 | pimon 全程 51–57 °C；`vcgencmd get_throttled` 始终 `0x0` |
| 供电不足 | 核心电压最低 0.8800 V，从未低于阈值；throttled 无 under-voltage 位 |
| 内存耗尽 | `systemd-oomd` **inactive**；三个 boot 里零 OOM 记录 |
| CPU 过载 | 掉线时 `load1` 已降到 0.00–0.01 |
| SD 卡故障 | `dd` 实测 31.2 MB/s；全程零 `mmc0` 错误 |
| 演示程序负载 | boot -1 期间 `chromium` 一次未启动，仍以同样方式掉线 |
| 演示服务的连接堆积 | boot -1 里 `ConnectionResetError` 为 0 次 |
| 笔记本自身 | 掉线时笔记本 650/585 Mbps、信号 81%、网关与其它设备均可达 |
| 内核崩溃 | 无 panic / oops / soft lockup 任何记录 |
| 正常关机 | 两次异常结束都没有 `Stopping` / `Reached target Shutdown` 之类流程 |

## 四、关键发现（按证据强度排序）

### 1. 系统一直活着，只是"入向不通"

`/var/log/pimon/pimon-YYYYMMDD.csv`（10 秒一行、`sync` 强制刷盘）在
"网络已断"之后仍在持续写入，`load` 一路降到 0.01，温度正常。
→ 机器没有卡死。

### 2. 双向性异常：树莓派能出去，笔记本进不来

`/var/log/wifi-watch.log` 在 17:31:48 之后仍然每 30 秒记录：

```
OK  assoc=yes signal=-64 freq=5520 gw=192.168.1.1 gwping=yes fails=0
```

即：**关联正常、信号 −59…−70 dBm、能 ping 通网关**。
但同一时刻，笔记本侧 `Get-NetNeighbor 192.168.1.66` 长期停在 `Probe`
（= 发出 ARP 请求但收不到任何应答）。

→ 这不是无线链路断开，而是"树莓派→网关"通、"笔记本→树莓派"不通。

### 3. `conflict detected` 与失联的时间关系

四个 boot 里共出现 4 次：

```
16:46:30   conflict detected for IP address 192.168.1.66 with host 00:00:00:00:00:00
17:01:31   同上
17:16:32   同上
17:31:43   同上
```

其中 17:01:31 → 17:01:37（6 秒）、17:31:43 → 17:31:48（5 秒）两处，
冲突日志之后数秒内即失联。另两次之后没有立即失联。

→ **相关性成立，因果性未证实。**

### 4. 每 15 分钟出现一次 —— 但原因未知

间隔为 901 s、901 s、911 s，非常规律。
**但已排除"DHCP 租约续租"这一解释**：`DHCP4.OPTION[3]: dhcp_lease_time = 86400`（24 小时），
T1 应是 12 小时，不可能是 15 分钟。周期来源**尚未查明**。

### 5. 地址本身没有被别的设备占用

掉线后笔记本 ARP 表里 `.66` 只有一条记录，MAC 为 `D8-3A-DD-4E-AB-D9`（树莓派本身）。
→ 不存在"另一台设备抢了 .66"。

### 6. 硬件看门狗确实存在且有效

`systemd[1]: Watchdog running with a hardware timeout of 1min.`、
`RuntimeWatchdogUSec=1min`、`RebootWatchdogUSec=2min`。
16:52:17 结束那次，下一次启动在 16:54:20，间隔 2 分 3 秒 ≈ 60 秒超时 + 开机。
→ 内核级冻结时它会自动复位，**不需要断电**（此前"必须断电才能恢复"的判断是错的）。

## 五、当前的结论

1. **这不是硬件故障、不是过热、不是供电、不是内存、不是 SD 卡、不是演示程序。**
2. **故障形态是"入向不可达"：树莓派自身一切正常且能主动发包，但网络不再把包送回给它。**
3. **根因尚未确定。** 剩下两个方向都没有证据可以排除：
   - **(a) AP/路由器侧停止向该 MAC 转发**（桥表老化、客户端隔离、无线间转发被阻断等）
   - **(b) 树莓派侧地址状态异常**（NetworkManager 的 ACD 误判后撤回地址声明）
4. 每 15 分钟一次的 `conflict detected` 是**目前唯一带时间规律的异常**，但规律来源未明。

## 六、尚未执行的检查（下一步）

- 在树莓派上装一个"入向探针"：每 10 秒从树莓派 `arping` 笔记本（`192.168.1.52`），
  失败即记录。这样下次故障时能立刻区分"AP 不转发"与"树莓派不回 ARP"。
- 用 `arping -D` 做重复地址检测，确认 ACD 报的冲突究竟是真是假。
- 若用户能进路由器管理页：查 DFS 事件日志、客户端隔离（AP Isolation）开关、`.66` 的 DHCP 保留设置。

## 七、对周三演示的建议

**不要试图在周三之前修好 Wi-Fi。改用有线。**

理由：本次排查已排除所有"能从树莓派侧修"的因素，剩下的都在路由器/无线环境一侧，
而那不是能在两天内可控解决的问题。一根网线可以整类消除该风险。

## 九、本次纠正的错误判断

| 曾经的错误结论 | 实际情况 |
|---|---|
| "必须断电才能恢复" | 有 60 秒硬件看门狗，内核冻结会自己复位（16:52 那次就是） |
| "整机卡死" | 网络断掉后系统仍在正常写盘，load 降到 0.01 |
| "ARP 显示 Reachable 所以它还活着" | 那是缓存假象，稳定状态是 `Probe`（解析失败） |
| "Chromium 拖死了它" | boot -1 里 Chromium 一次没跑，照样掉线 |
| "15 分钟的周期是 DHCP 租约续租" | 租期 86400 秒，"续租"解释不成立，已撤回 |
| "2.4G 钉住算成功" | 只跑了 3 分钟，时间太短，**证不了**是否解决 |
